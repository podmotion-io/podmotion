# DEFECT-2026-06-15 — pycriu MagicException on ifaddr image (unknown CRIU image magic)

**Status:** Open
**Protocol:** §14b Human/Monitor-Found Defect (opened immediately, no severity threshold)
**Found by:** Monitor agent during `gate33-strict-tcp`
**Component:** `internal/agent/server/server.go` → `patchCheckpointImages` (embedded Python `pm-patch-ckpt.py`)
**Author of report:** Opus QA Architect

---

## 0. Correction to the reported numbers

The defect ticket asserted `1194725922 == 0x47498042`. **This is incorrect.**

```
1194725922 decimal = 0x47361222 hex   (verified)
0x47498042 hex      = 1196033602 decimal
```

The hex in the original report is a transcription error. All analysis below uses the **decimal magic `1194725922` (0x47361222)** that pycriu actually reported, since `MagicException` is constructed with the raw `img_magic` integer (`images.py:67`, `images.py:571`).

The failing source location was also slightly off: the error is at **embedded-script line 121**, which is the **ifaddr** block, not a mountpoints block:

```python
116  # ---- ifaddr: remove source pod IP addresses; keep loopback only (ADR-0125, ADR-0162) ----
117  ifaddr_path = os.path.join(ckpt, 'ifaddr-10.img')
118  if os.path.exists(ifaddr_path):
119      src = backup(ifaddr_path)
120      with open(src, 'rb') as f:
121          img = pycriu.images.load(f)     # <-- raises MagicException(1194725922)
```

---

## 1. Defect class and magic-number identity

**Class:** Unhandled `pycriu.images.MagicException` — unknown CRIU image magic, stale vendored magic table.

**Magic identity:** `1194725922` (`0x47361222`).

- It is **not present in `pycriu/images/magic.py`** — neither in `by_val` nor `by_name`. (`grep 1194725922 pycriu/images/magic.py` → not found.)
- There is **no `IFADDR` entry of any kind** in the vendored magic table — `by_name['IFADDR']` does not exist.
- The image being read is `ifaddr-10.img`. CRIU writes ifaddr images with a `IMG_SERVICE` first-magic followed by the `IFADDR` second-magic. pycriu's reader (`images.py:__rhandler`, lines 561–571) consumes the `IMG_SERVICE` first-magic, reads the second magic, looks it up in `magic.by_val`, misses, and raises `MagicException(img_magic)`.

So `1194725922` **is** the CRIU `IFADDR` image magic. The vendored `pycriu/images/magic.py` (header: `#Autogenerated. Do not edit!`) was generated from a CRIU version **older than the one producing these checkpoints** and never included `IFADDR`. The last entries in the table are `IRMAP_CACHE` / `KDAT`; `IFADDR`, `AUTOFS`-adjacent and several newer types are missing relative to current CRIU.

---

## 2. Root cause

`patchCheckpointImages` ships a **vendored, frozen copy of pycriu** (`pycriu/images/magic.py` + `images.py`) whose `magic` table does not include the `IFADDR` image type. The runtime CRIU (4.2 per CLAUDE.md / ADR-0132) emits an `ifaddr-10.img` whose second-magic `1194725922` has no `by_val` mapping. `pycriu.images.load()` therefore raises `MagicException`, the embedded script has **no exception handling around the load**, Python exits 1, and `patchCheckpointImages` surfaces:

```
restore failed: patch checkpoint images: patch script failed: exit status 1
```

This is a **CRIU-vs-pycriu version skew**: CRIU advanced its image-type set; the vendored pycriu magic table did not track it.

A second, compounding root cause: the script's ifaddr/netns/netdev/mountpoints blocks each call `pycriu.images.load(f)` **with no try/except**. A single unknown image magic is fatal to the entire patch step even though the affected image (ifaddr) is one PodMotion intends to rewrite anyway.

---

## 3. Systemic vs isolated

**Systemic.**

Reasons:

1. The missing entry is not a one-off corrupt image — it is a *whole CRIU image type* (`IFADDR`) absent from the vendored magic table. **Every** checkpoint that CRIU produces with an ifaddr image (i.e. every networked pod, which is all of them) will hit this once the ifaddr block runs against a CRIU newer than the table.
2. The magic table is `#Autogenerated. Do not edit!` and stale by an unknown delta. Any **other** newer image type CRIU emits (the table stops around `KDAT`/`IRMAP_CACHE`; newer CRIU adds more) will trip the same unguarded `load()` the moment the script (or any future `pycriu` use) touches it.
3. The failure is deterministic and version-coupled, not data-dependent. It will recur on every `gate*-strict` run on this CRIU until the table or the load path is fixed.

It only *appeared* isolated because the ifaddr block is gated on `os.path.exists('ifaddr-10.img')` and is near the end of the script — earlier mountpoints/netns/netdev images happened to all be in the (older) magic table, so the script reached line 121 before dying.

---

## 4. Pipeline gap (the missing test)

**`patchCheckpointImages` has zero test coverage.** `grep -rln patchCheckpointImages` across `internal/` and `test/` returns only `server.go` itself. There is:

- **No unit test** that runs the embedded Python script against a fixture set of real CRIU images.
- **No golden-image / corpus test** that asserts the vendored pycriu `magic.by_val` covers every image type produced by the pinned CRIU version.
- **No version-pin assertion** comparing CRIU's image-type set to pycriu's `magic.py`.

The test that **would** have caught this:

> A corpus test that runs `criu dump` on a representative networked pod with the **pinned CRIU build**, then runs `pm-patch-ckpt.py` (or directly iterates every `*.img` through `pycriu.images.load`) and asserts no `MagicException`. This is exactly the §8 Step 0.5 corpus-conflict-scan class of check, applied to the patch step.

Because there was no such test, the first thing to exercise the ifaddr image path against the current CRIU was the **monitor agent at gate33** — i.e. the defect escaped the entire pipeline to runtime.

---

## 5. Proposed fix

Layered; do all three:

**(A) Make the script resilient to unknown magics (immediate, blast-radius containment).**
Wrap each `pycriu.images.load()` in try/except. For an image PodMotion only *strips/rewrites* (ifaddr, netns, netdev), an unknown magic should **not** be fatal — log and skip, leaving the `.orig` in place, rather than aborting restore. For images PodMotion *must* rewrite to succeed (mountpoints), an unknown magic should fail loudly but with a clear "vendored pycriu magic table is stale for image X (magic N)" message, not a bare `exit status 1`.

**(B) Refresh the vendored pycriu magic table to the pinned CRIU version (correct fix for this instance).**
Regenerate `pycriu/images/magic.py` (and `pb2`/handlers as needed) from the CRIU version baked into the agent image so `IFADDR` (1194725922) and any other newer types resolve. Pin both CRIU and pycriu and assert they match.

**(C) Prefer named-file targeting over blind iteration where possible.**
The ifaddr/netns/netdev blocks already open specific named files — good. The **mountpoints** block uses `glob('mountpoints-*.img')`. Keep the named-file discipline and never expand the script to a blanket "open every `*.img`" loop, which would maximize exposure to unknown magics.

Plus a **new test (Step 4 gap closure):** corpus scan over a real pinned-CRIU checkpoint asserting `pycriu.images.load` succeeds (or is explicitly skipped) for every image the patch step touches. Make it blocking in the gate (§8 Step 0.5 class).

---

## 6. §4a evaluation — is `patchCheckpointImages` a brittle chain?

**Yes — it is a brittle chain by §4a, on multiple axes:**

1. **Hidden cross-component version coupling.** Correct operation silently depends on `vendored-pycriu.magic` ⊇ `runtime-CRIU.image-types`. Nothing asserts or even surfaces this contract; it is discovered only by runtime failure. A frozen `#Autogenerated. Do not edit!` table coupled to an independently-upgradable CRIU binary is the canonical brittle-chain shape.
2. **All-or-nothing fault propagation.** One unknown magic on one image aborts the entire patch step (and thus restore), even for images PodMotion was going to overwrite. No isolation between the independent mountpoints/netns/netdev/ifaddr sub-steps.
3. **Stringly-typed failure surface.** The failure reaches the operator as `patch script failed: exit status 1` + stderr blob — a Python traceback marshaled through a subprocess. There is no typed error, no image-name, no magic value in the Go-side error; root-causing required reading the embedded script and decoding the magic by hand.
4. **Untested critical path.** A subprocess that hand-edits binary CRIU images on the restore-critical path, with zero automated coverage, is fragile by construction — the patch logic embeds deep CRIU image-format assumptions (`ext_key`, `mnt_id`, `link.type==772`, `ifindex==1`) that drift silently as CRIU evolves.

**Recommendation:** Treat the pycriu-magic/CRIU coupling as a first-class pinned contract with a blocking corpus test (fix B+test), and add per-sub-step fault isolation (fix A) so the chain degrades gracefully instead of failing whole. Longer term, evaluate replacing the embedded-Python-edits-binary-images approach with a typed, in-process image manipulation path to remove the subprocess/stringly-typed brittleness entirely.
